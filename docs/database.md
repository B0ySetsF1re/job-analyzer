# Database

## Overview

Postgres 18 (Docker Compose locally), accessed through **SQLAlchemy 2.0 async** with the
**psycopg 3** driver. Schema changes are managed by **Alembic** migrations.

Decisions (see CLAUDE.md → DB decisions):
- SQLAlchemy, not SQLModel — ORM models stay separate from API Pydantic schemas
- psycopg 3 is the only driver (Procrastinate in Phase 2 uses it too)
- LLM-extracted data goes into a JSONB column; fields get promoted to real columns only
  when filtering/indexing needs them
- UUID primary keys generated by Postgres (`gen_random_uuid()`)

NestJS parallels: SQLAlchemy ≈ TypeORM/MikroORM, Alembic ≈ TypeORM migrations,
engine ≈ `DataSource`, `AsyncSession` ≈ an `EntityManager` scoped to one request.

## Mental Model: Engine and Session

Both exist in NestJS too — `@nestjs/typeorm` just creates them for you, so they rarely
appear by name.

### Engine = how to reach the DB (the connection pool)
- Knows the URL and driver, and holds a **pool of open connections**
- **One per process**, long-lived: created on first use, closed on shutdown
- You almost never use it directly — sessions borrow connections from it
- NestJS: TypeORM's `DataSource` (what `TypeOrmModule.forRoot()` creates), or `new Pool()`
  in `pg`

### Session = one unit of work (one transaction)
- **Short-lived: one per request.** Borrows a connection and opens a transaction
- **Tracks objects:** everything you load or `session.add()`, including later attribute
  changes
- **Writes everything at once:** `commit()` sends all pending INSERT/UPDATE/DELETE and
  commits. Closing without commit **rolls back**
- **Identity map:** loading the same row twice in one session returns the *same* Python
  object, not two copies
- NestJS: MikroORM's `EntityManager` (`em.persist()` + `em.flush()` is the same idea), or a
  TypeORM `EntityManager` inside `dataSource.transaction(...)`

```python
posting = Posting(source="linkedin", raw_text="...")
session.add(posting)          # nothing sent to the DB yet, only tracked
posting.status = "pending"    # still nothing sent
await session.commit()        # now: INSERT ...; COMMIT
```

**Difference from TypeORM repositories:** `await repo.save(entity)` hits the DB immediately
in its own transaction. A session *accumulates* changes and commits them together, so
multi-table changes are atomic without writing `transaction(...)` by hand.

### Lifecycle in this app

```
process start
   └─ get_engine()  → AsyncEngine + connection pool           (one, until shutdown)

each request to an endpoint with Depends(get_session):
   ├─ get_session() opens an AsyncSession → borrows a connection, begins a transaction
   ├─ handler: session.add(...), await session.execute(select(...)), await session.commit()
   └─ after the response: session closes → connection back to the pool
                                           (anything uncommitted is rolled back)

shutdown
   └─ lifespan → dispose_engine() → pool closed
```

### Transactions
Add every change to the same session and **commit once at the end** — all-or-nothing:

```python
session.add(posting)
profile.updated_at = now()        # loaded earlier through the same session
session.add(match_result)
await session.commit()            # one transaction for all three
```

| What fails | Result |
|---|---|
| DB error (unique, FK, ...) during flush/commit | Exception raised, transaction aborted, nothing saved |
| Python error before `commit()` | `commit()` never runs; `get_session` closes the session → rollback |
| Either | Exception propagates → FastAPI returns 500; no manual `try/rollback` needed |

Explicit transaction block, the `dataSource.transaction(async (em) => ...)` equivalent —
useful only when one request needs *several separate* transactions:

```python
async with session.begin():       # commits on normal exit, rolls back on exception
    session.add(a)
    session.add(b)
```

**Flush vs commit:** `await session.flush()` sends pending SQL *inside* the open
transaction (others still can't see it); `commit()` flushes and then ends the transaction.
Queries auto-flush first (**autoflush**), so they see your own pending changes.

## Code: `app/db.py`

| Piece | What it is | NestJS / TypeORM parallel |
|---|---|---|
| `Base(DeclarativeBase)` | Parent class for all ORM models; `Base.metadata` holds the table definitions | `@Entity()` registry |
| `get_engine()` | One `AsyncEngine` per process, owns the connection pool; `@lru_cache` = created lazily, once | `DataSource` |
| `get_sessionmaker()` | Factory for `AsyncSession` objects | `dataSource.createEntityManager` |
| `get_session()` | FastAPI dependency: one session per request, closed after the response | request-scoped `EntityManager` |
| `dispose_engine()` | Closes pooled connections; called from the app's `lifespan` on shutdown | `onApplicationShutdown` |

Handlers receive a session the same way they receive settings:

```python
session: Annotated[AsyncSession, Depends(get_session)]
```

- **Commit is explicit.** If a handler doesn't commit, closing the session rolls back
- **`expire_on_commit=False`:** after commit, objects keep their loaded values. The
  default (expire + reload on access) would trigger an implicit query, which async
  SQLAlchemy forbids
- `get_session` is an async generator (`yield`) — the same setup/teardown pattern as the
  pytest `client` fixture, used by FastAPI for dependencies

### `DATABASE_URL` vs the SQLAlchemy URL
- `DATABASE_URL` stays plain libpq style: `postgresql://user:pass@host:5432/db`
- `sqlalchemy_url()` rewrites it to `postgresql+psycopg://...` — SQLAlchemy needs the
  driver name, but psycopg itself (used directly by Procrastinate) rejects the `+psycopg`
  suffix. One env var, two consumers

### Lifespan
`app/main.py` passes `lifespan=` to `FastAPI()`. It's an async context manager: code before
`yield` runs on startup, code after runs on shutdown (NestJS `onModuleInit` /
`onApplicationShutdown` in one function).

## Models

```python
class Posting(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "postings"

    raw_text: Mapped[str] = mapped_column(Text)                     # NOT NULL
    extraction: Mapped[dict[str, Any] | None] = mapped_column(JSONB)  # nullable
```

| SQLAlchemy | Meaning | TypeORM parallel |
|---|---|---|
| `Mapped[str]` / `Mapped[str \| None]` | Python type; also decides NOT NULL vs nullable | property type + `nullable` |
| `mapped_column(Text, ...)` | SQL type and options; type optional when inferable | `@Column({ type: "text" })` |
| `server_default=func.now()` | `DEFAULT now()` in the DDL; Postgres fills it in | `default: () => "now()"` |
| `onupdate=func.now()` | SQLAlchemy adds `updated_at = now()` to its UPDATEs | `@UpdateDateColumn` |
| Mixin class | Columns copied into every model that inherits it | Abstract base entity |
| `sort_order=` | Column position (mixin columns otherwise go last) | — |

### Tables

| `postings` | Type | Notes |
|---|---|---|
| `id` | `uuid` | PK, `gen_random_uuid()` |
| `source` | `text` | Where it came from (`linkedin`, a URL, ...) |
| `raw_text` | `text` | The posting as submitted |
| `status` | `varchar(32)` + CHECK | `pending` (default) / `processed` / `failed` |
| `extraction` | `jsonb`, nullable | `PostingExtraction` from the LLM; NULL until processed |
| `error` | `text`, nullable | Why processing failed |
| `created_at`, `updated_at` | `timestamptz` | `now()`; `updated_at` refreshed on every UPDATE |

`profiles`: `id`, `raw_text` (the CV), `data` (parsed profile, nullable `jsonb`), timestamps.

### Status: VARCHAR + CHECK, not a native ENUM
`Enum(PostingStatus, native_enum=False, create_constraint=True, ...)` stores a plain string
and adds `CHECK (status IN ('pending', 'processed', 'failed'))`. In Python it's still a
`PostingStatus`. Chosen over `CREATE TYPE ... AS ENUM` because changing the allowed values
later is a two-line, reversible migration (drop + recreate the constraint), while native
enums can't drop values and `ALTER TYPE ... ADD VALUE` can't be undone. Neither is detected
by autogenerate (see Gotchas).

### `eager_defaults`
`TimestampMixin` sets `__mapper_args__ = {"eager_defaults": True}`: DB-generated values come
back via `RETURNING` on UPDATE as well, not only on INSERT. Otherwise `updated_at` is
expired after an UPDATE and reading it raises `MissingGreenlet`.

## Migrations (Alembic)

```bash
make db                                  # Postgres must be running
make migration MSG="add postings table"  # autogenerate from model changes
make migrate                             # apply all pending (alembic upgrade head)
```

Other useful commands (from `backend/`):

| Command | Does |
|---|---|
| `uv run alembic current` | Revision the DB is at |
| `uv run alembic history` | All revisions |
| `uv run alembic downgrade -1` | Undo the last migration |
| `uv run alembic upgrade head --sql` | Print the SQL instead of running it (offline mode) |

### How autogenerate works
1. `env.py` imports `app.models`, which imports every model → tables registered on
   `Base.metadata`
2. Alembic connects to the DB and compares the live schema with `Base.metadata`
3. It writes the difference as `op.create_table(...)` / `op.add_column(...)` calls into a new
   file in `migrations/versions/`
4. Post-write hooks run `ruff check --fix` + `ruff format` on the file

**Always read the generated migration before applying it** — autogenerate is a diff tool,
not a mind reader (see Gotchas).

### Configuration
- `[tool.alembic]` in `pyproject.toml`: script location, date-prefixed file names
  (`2026_10_25_1422-<rev>_<slug>.py`, sorted chronologically), ruff post-write hooks
- `alembic.ini` only holds logging config. There is no `sqlalchemy.url` in it: `env.py`
  reads `DATABASE_URL` from app settings, so the app and migrations can't drift apart
- `script.py.mako` uses modern type hints (`str | None`) so new files pass ruff as-is

### Naming convention
`Base.metadata` has a `naming_convention` (`pk_postings`, `ix_postings_status`,
`fk_<table>_<col>_<ref>`, ...). Without it, Postgres invents constraint names, and a later
migration that alters or drops a constraint has no reliable name to refer to.

## Testing with the Database

DB tests run against a real Postgres. There is no SQLite or in-memory fake, because JSONB,
`gen_random_uuid()` and CHECK constraints behave differently there or don't exist.
`make test` runs `make db` first, so the container is always up.

```
pytest start (once)
   └─ test_database_url: DROP + CREATE <db>_test → alembic upgrade head

each test that asks for db_session
   ├─ new connection → BEGIN
   ├─ test runs; session.commit() only releases a SAVEPOINT
   └─ ROLLBACK → the next test sees empty tables
```

| Fixture | Scope | What it gives you |
|---|---|---|
| `test_database_url` | session (once per run) | URL of a freshly migrated `job_analyzer_test` DB |
| `db_session` | function (per test) | `AsyncSession` inside a transaction that is always rolled back |
| `anyio_backend` | function | Makes `@pytest.mark.anyio` tests run on asyncio |

```python
@pytest.mark.anyio
async def test_something(db_session: AsyncSession) -> None:
    db_session.add(Posting(...))
    await db_session.commit()   # fine: the outer transaction is still rolled back
```

- **Separate database, same server:** the name comes from `DATABASE_URL` plus `_test`, so
  your dev data is never touched
- **Schema built by the migrations, not `create_all()`.** Every test run proves the
  migrations work on an empty database
- **`test_migrations_match_models`** runs the same diff as `make migration`: test DB (from
  migrations) vs models. It fails if you changed a model and forgot the migration
- **`join_transaction_mode="create_savepoint"`** is SQLAlchemy's recipe for "joining a session
  into an external transaction". NestJS parallel: a TypeORM `queryRunner` transaction started
  in `beforeEach` and rolled back in `afterEach`
- `pytest.mark.anyio` comes from the anyio plugin (installed with FastAPI). Jest runs
  `async` tests natively; pytest needs this marker

## Gotchas

### DB tests fail with "connection refused" when run without make
- `uv run pytest` doesn't start Postgres; `make test` does. Run `make db` once, then plain
  pytest works too. Non-DB tests (health, config) don't need Postgres

### `test_migrations_match_models` fails with `add_table` / `add_column` in the diff
- You changed a model but have no migration for it: `make migration MSG="..."`, review the
  file, rerun the tests. The diff in the message lists what's missing

### "Failed: async def functions are not natively supported"
- **Cause:** an `async def` test without the `@pytest.mark.anyio` marker. pytest itself
  can't await coroutines; the anyio plugin only handles marked tests
- **Fix:** add the marker (or `pytestmark = pytest.mark.anyio` at the top of the module)

### A new model isn't picked up by autogenerate
- **Cause:** the model module isn't imported anywhere `env.py` can see, so its table never
  gets registered on `Base.metadata`
- **Fix:** import it in `app/models/__init__.py`

### Autogenerate misses or misreads some changes
- It does **not** detect: column/table renames (shows as drop + add — data loss!), some
  server default changes, changes inside CHECK constraints, enum value changes
- **Fix:** review every generated file; edit renames into `op.alter_column(...,
  new_column_name=...)` by hand

### Committing after every step breaks atomicity
- Every `commit()` ends a transaction. `add(a); commit(); add(b); commit()` — if the second
  commit fails, `a` stays saved
- **Fix:** one `commit()` at the end of the unit of work. The usual slip when coming from
  TypeORM's `save()`-per-entity style

### DB errors raised from a query line, not from `commit()`
- **Cause:** autoflush — before `await session.execute(select(...))` the session sends
  pending INSERT/UPDATE, so e.g. a unique violation surfaces on that line
- Data is still safe (same uncommitted transaction); only the error location differs.
  Use `with session.no_autoflush:` (plain `with`, even on `AsyncSession`) if a query must
  not flush

### `posting.id` is `None` right after `session.add(posting)`
- **Cause:** UUIDs are generated by Postgres (`gen_random_uuid()`), so the value exists only
  after the INSERT
- **Fix:** `await session.flush()` — sends the INSERT inside the open transaction and fills
  in `id`; use it (e.g. as a foreign key), then `commit()` everything together

### "current transaction is aborted, commands ignored until end of transaction block"
- **Cause:** a statement failed (e.g. `IntegrityError`) and the error was caught; Postgres
  refuses every further statement in that transaction
- **Fix:** `await session.rollback()` before using the session again:
  ```python
  try:
      await session.commit()
  except IntegrityError:
      await session.rollback()
      raise HTTPException(409, "duplicate") from None
  ```

### Rollback doesn't undo side effects
- Only DB changes are transactional. An LLM call, email or job enqueued over another
  connection has already happened if the commit then fails
- **Rule:** commit first, then trigger side effects (relevant in Phase 2: save the posting,
  then enqueue the Procrastinate job)

### `Posting(...).status` is `None` before flush
- **Cause:** `server_default` is applied by Postgres at INSERT time; the Python object has no
  value until `flush()`/`commit()` returns it. Same for `id`, `created_at`, `updated_at`
- **Fix:** flush before reading DB defaults (TypeORM behaves the same way before `save()`)

### Enum column stores `"PENDING"` instead of `"pending"`
- **Cause:** SQLAlchemy's `Enum` stores member **names** by default
- **Fix:** `values_callable=lambda e: [m.value for m in e]`

### Non-native `Enum` creates no CHECK constraint
- **Cause:** `create_constraint` defaults to `False` (since SQLAlchemy 1.4), so any string is
  accepted by the DB
- **Fix:** `create_constraint=True` plus a `name=` (the naming convention builds
  `ck_<table>_<name>` from it)

### Adding a status value: autogenerate sees nothing
- New `PostingStatus` member → no migration is generated, and the old CHECK rejects the new
  value with `IntegrityError`. Write the migration by hand:
  ```python
  op.drop_constraint(op.f("ck_postings_posting_status"), "postings", type_="check")
  op.create_check_constraint(
      op.f("ck_postings_posting_status"),
      "postings",
      "status IN ('pending', 'processing', 'processed', 'failed')",
  )
  ```
  Keep values ≤ 32 chars (`length=32`)

### `op.drop_constraint(...)`: constraint "ck_postings_ck_postings_..." does not exist
- **Cause:** in migrations, the naming convention is applied to names you pass to `op.*` too,
  so a full name gets the prefix twice
- **Fix:** wrap full names in `op.f("...")` ("final name, don't convert"). Autogenerate
  already does this (`name=op.f("pk_postings")`)

### Changing a key inside a JSONB dict isn't saved
- `posting.extraction["company"] = "Acme"` mutates the dict in place; SQLAlchemy only tracks
  attribute *assignment*, so no UPDATE is sent
- **Fix:** assign a new dict: `posting.extraction = {**posting.extraction, "company": "Acme"}`
  (or use `MutableDict.as_mutable(JSONB)` if in-place edits become common)

### `created_at == updated_at` even after an update (in tests)
- Postgres `now()` is the **transaction start** time. Insert and update in one transaction
  (every test runs in one) get the same timestamp. Use `clock_timestamp()` if you ever need
  wall-clock time

### `MissingGreenlet` / "greenlet_spawn has not been called"
- **Cause:** something triggered implicit I/O in async code — usually accessing a lazy
  relationship or an expired attribute
- **Fix:** load relationships explicitly (`selectinload(...)`) and keep
  `expire_on_commit=False`

### `make migrate` fails with "connection refused"
- Postgres isn't running: `make db` first. Migrations run from the host, so they use
  `DATABASE_URL` from `.env` (host `localhost`)

### `ruff check` reports "1 remaining" while generating a migration
- Harmless: the `ruff_check` hook runs before `ruff_format`, and the remaining issue
  (template whitespace) is fixed by the format hook right after
